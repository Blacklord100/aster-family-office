# Document engine configuration

Engine selection and processing mode are independent. Both classical workflow and the bounded agent can use an installed Ollama model, OpenAI Responses, or Anthropic Messages. The deployment default remains local; no cloud credential is needed to use it. Local structured JSON can drive the bounded document planner without native tool calling: read pages, search, inspect layout or source images, extract, review coverage and finish. These actions do not send mail, run commands, browse arbitrary URLs or post financial changes.

## Profiles and job identity

Owners/admins manage profiles in the Engines panel. Other members see public metadata only. Local discovery reads the fixed deployment Ollama endpoint through the authenticated processor; it never downloads a model. A local model is checked for GGUF format and absence of remote-host/model metadata before inference. Model tags are operator-selected, bounded strings; this check is not an accuracy or model-license certification.

Each profile change creates a new immutable configuration revision. Editing does not silently activate it. Activation requires the current revision; concurrent edits produce a conflict. The deployment-default button restores the configured local model. An active profile cannot be deleted until another engine is activated. Deleting an inactive profile hides it; encrypted historical revisions and job credentials remain retained for reproducibility/retries. Removing a profile is not key destruction or provider-side revocation.

Uploads and imported mailbox documents pin provider, model tag, execution location, profile revision and encrypted credential configuration when the job is created. Changing mode or active engine affects newly created jobs. Retrying a failed/cancelled job keeps its pin; upload again after selecting another engine to request a different configuration. Duplicate pending uploads reuse a job only for the same document, mode and engine snapshot. Model tags/API aliases can resolve to changed weights: this pins configuration, **not immutable model artifact bytes**. Discovery exposes available digests for operator verification.

Historical jobs without a recorded engine expose `engineLegacy: true`. A queued or explicitly retried legacy job captures the deployment-local default at its next worker claim, then retains that pin. It never borrows the active cloud profile. That new pin says nothing about the engine used in an earlier historical attempt. New jobs with a missing pin are rejected by both SQL constraints and the worker.

Secrets are AES-256-GCM encrypted with tenant/record/revision context, including a separate encrypted copy for each job. DTOs, audit entries, provider-check errors and extraction results exclude credentials. Only authenticated internal calls carry them to the selected processor, then to the fixed provider API. Child processes receive a minimal environment without processor/database/provider service secrets; the selected job credential travels through private stdin. Host administrators, process memory/core dumps and key recovery remain trusted operational boundaries.

## Inspect runtime metadata

Administrators can inspect the exact selected revision, including an older saved revision that remains active, or the current revision of a saved profile. The browser sends only the target, expected profile ID and revision. The server verifies that selection in the tenant, releases the database transaction, then calls the configured processor. Concurrent selection changes produce a conflict. Inspection is rate limited to 20 requests per organization per minute, authenticated, body bounded and cancelled when the caller disconnects; the processor has a separate 20-second inspection deadline.

The panel distinguishes locally advertised image support, effective deployment enablement and image testing. Missing capabilities remain unknown. An exact local alias can advertise vision without establishing image extraction quality; this check sends no image and generates no text. A text connectivity/schema test remains a separate synthetic generation request. Current cloud adapters are text only, and metadata inspection never queries their providers. Both workflow and agentic execution retain the same privacy boundary for a selected engine.

Expandable details show the processor's actual document, OCR, image, email-tree, model-call, action and time ceilings. Local calls request 16,384 context tokens and 3,200 output tokens with an 11,500-byte system/source/schema prompt guard. Cloud output requests are also capped at 3,200 tokens; provider context limits are not inspected. Ceilings do not guarantee full document coverage. An optional local digest is only an exact-alias observation at the displayed time, **not an immutable weights pin for jobs**. Refresh the inspection after replacing a model or changing deployment settings.

## Enable cloud deliberately

The selected cloud processor receives the original uploaded file and its pinned engine configuration. It decodes the document and sends bounded source text to the model provider. Place this processor within the boundary you intend to trust; selecting a local model alone does not establish the privacy of your wider hosting and mailbox setup.

1. Leave the default local processor and Ollama on `local-confidential`, with `ALLOW_CLOUD_ENGINES=false` and `OLLAMA_NO_CLOUD=1`. Do not add internet access to that network to enable cloud engines.
2. Provision a separate instance of the same processor image for cloud work. Set its `ALLOW_CLOUD_ENGINES=true`, supply the internal `PROCESSOR_TOKEN`, and give it a private caller network plus controlled provider egress. Do not attach it to the Ollama/local-confidential network. It needs no database credentials or persistent document volume. Use the same nonroot, read-only/tmpfs, capability, resource and no-access-log restrictions.
3. Configure `ALLOW_CLOUD_ENGINES=true` and `PROCESSOR_CLOUD_URL` on the web and document worker. Cloud readiness requires both settings and a different processor origin. HTTPS is mandatory for remote processor hosts; HTTP is permitted only for explicit loopback/deployment service names. Different origins alone do not establish physical isolation; verify actual network membership, DNS/firewall policy, TLS and authentication on the target host.
4. In the panel, create a profile with an authorized provider key and explicit model identifier. Run its synthetic check, then activate it while acknowledging that decoded document text may leave the deployment. Review organizational permissions, provider terms, retention, regions and budgets first. Do not paste keys into URLs, logs, source control or browser storage.

The supplied default Compose stack remains local-only. The optional cloud processor must be provisioned and verified by an operator; changing application flags does not grant an isolated container internet access. The mailbox collection worker's internet network is separate and must not become an inference route. Disabling deployment cloud permission blocks pinned cloud jobs; it never silently reroutes them locally.

## Provider requests and validation

OpenAI uses only `https://api.openai.com/v1/responses`, with `text.format` JSON Schema, `strict: true`, `max_output_tokens: 3200` and `store: false`. A named Codex model here is a Responses model, not an unattended Codex CLI or shell. `store: false` does not promise zero provider retention; account-level retention controls and provider policy still apply. [Structured outputs](https://developers.openai.com/api/docs/guides/structured-outputs), [GPT-5.3-Codex model](https://developers.openai.com/api/docs/models/gpt-5.3-codex), [data controls](https://developers.openai.com/api/docs/guides/your-data).

Anthropic uses only `https://api.anthropic.com/v1/messages`, `output_config.format` JSON Schema and `max_tokens: 3200`. Provider-compatible schemas wrap planner unions in an object and simplify unsupported constraints; the original strict financial/date/evidence schema is still checked locally. Model/account support is tested explicitly; an unsupported model does not trigger a substitute. [Anthropic structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs).

Provider HTTP clients ignore inherited proxy settings, refuse redirects, cap response bytes and never run returned tool calls. Refusals, incomplete responses and invalid envelopes fail closed. Independently valid financial candidates may survive an invalid sibling, but each still passes unchanged source evidence checks. Provider errors produce bounded safe codes, never raw error bodies. Workflow source parsing remains local; cloud selection permits sending only the bounded model prompts/source windows required by that pipeline.

The configured model inactivity timeout and 590-second total document deadline remain enforced. Both modes share `MAX_MODEL_CALLS` (default 64, maximum 96) and per-page extraction limits; agent planning also has `MAX_AGENT_STEPS` (default 32, maximum 64). The synthetic text check has a separate 140-second process deadline and one model call. Processor-busy responses defer a job for 30 seconds without charging one of its three extraction failure attempts, capped at 30 capacity deferrals. No automatic provider retry or fallback is hidden inside an adapter.

## Evidence and remaining checks

Focused tests use a loopback Ollama server and mock cloud HTTP transports. They check provider request shapes, disabled-cloud rejection, credential/tenant context, redirect refusal, schema salvage, profile/job revision behavior, permission gates and bounded capacity deferral. Optional database checks run with `ASTER_ENGINE_INTEGRATION=1` on the explicitly authorized Aster test cluster after migration; do not point them at unrelated databases. Test completion is reported in the release validation record.

The local synthetic Gemma probe validated one allowed `read_page(page=1)` structured result in 8.791 seconds. That is connectivity/schema evidence only. Real cloud credentials were unavailable, so cloud authentication, account/model availability, billing, latency, provider retention settings and extraction accuracy remain unverified. Local end-to-end results are recorded separately by the release owner. Previously frozen evaluation reports remain unchanged and do not test these new adapters. Docker build/boot and provider network enforcement remain target-host checks.


The development deployment defaults to the locally installed `gemma4:e4b-m3` model. `OLLAMA_MODEL` is an explicit deployment override; activating a saved profile overrides that default for new jobs only. Existing job snapshots and profile revisions are retained. Switching defaults never downloads weights. The offline installer continues to use `aster-approved:gguf`, the operator-imported and verified model alias; import your approved Gemma weights into that alias or set `OLLAMA_MODEL` to their installed tag. Gemma is the selected default, not a claim that it outperforms every alternative: the latest synthetic 100-mail comparison recovered 90/90 expected observations in all four Gemma/Qwen and workflow/agentic cells.
